# Repository binary payload audit

Audit date: 2026-08-27

## Scope and policy

The audit covered every tracked file below `Resources`, plus the repository-root
`Prepare Exe.rar`. Executable code, compiled libraries, type libraries, and
dependency archives must not be committed. Release tooling must instead obtain
dependencies from an authoritative HTTPS source, verify a repository-pinned
digest, and record provenance.

Images, icons, fonts, and application data are binary-format assets but are not
executable payloads. The application needs those source assets, so they remain
tracked. The retained set consists of SVG, PNG, GIF, ICO, OpenSans TTF, and the
ISO language JSON file.

## Verified dependency acquisition

Windows release packaging uses MKVToolNix 101.0 from the official publisher
release directory:

- Archive: `https://mkvtoolnix.download/windows/releases/101.0/mkvtoolnix-64-bit-101.0.zip`
- Publisher checksum: `https://mkvtoolnix.download/windows/releases/101.0/mkvtoolnix-64-bit-101.0.zip.sha256`
- Pinned SHA-256: `59a807b45b34ac524dfdef61edcf0642ee9bd6b08c130cfc078532c362569abc`

`scripts/fetch_mkvtoolnix.py` requires both the live publisher sidecar and the
value in `packaging/dependencies.json` to agree before downloading. It verifies
the archive again, selectively extracts `mkvmerge.exe`, `mkvpropedit.exe`, the
license, and readme into the build directory, and writes `PROVENANCE.json`.
`build_release.ps1` then executes both tools and requires their reported version
to match the manifest before PyInstaller runs.

An explicitly supplied offline archive can be staged with `--archive`; it still
must match the pinned SHA-256. This mode exists for deterministic tests and
air-gapped rebuilds where the artifact has already been obtained securely.

## Enforcement and history

`tests/test_binary_policy.py` rejects executable/archive extensions and PE,
ELF, or RAR signatures across the tracked tree. `.gitignore` also blocks common
dependency payload extensions and keeps `Resources/Tools` documentation-only.

Removing a file from the current tree does not remove old objects from Git
history. A history rewrite would disrupt existing clones and release references
and is intentionally outside this change. It should be considered separately
only if repository-size reduction or removal of a sensitive payload is needed.
